# Root-Cause Lifecycle Interrogation (진단 추론 — L2→근본원인 다리)

핵심 명제 (이 한 줄이 전부):
> **버그 = "소비자가 쓰는 값 == 생산자가 마지막으로 쓴 값" 불변식이 *어느 edge*에서 깨진 것.**
> 값의 모든 edge를 빠짐없이 열거하면 깨진 곳을 못 놓친다.

**언제**: "값이 틀리다 / stale 하다 / 변경이 반영 안 된다" 류 버그 진단(diagnose, bugfix 사이클).
**아닐 때**: 새 기능 설계(→ planner §5.2b), 프로토콜 모양·합의 안전성 판정(→ domain-pack invariants backstop).
**관계**: cks를 대체하지 않는다. cks가 *후보 코드*를 주면, 이 절차가 *인과 사슬*로 조립한다.

## 절차 (이 순서를 강제한다)

0. **팩 지식 선소비 (있으면)** — EvidencePack의 invariant/convention 청크는 "정상 행동의 명세"다.
   (a) 증상 관련 규칙을 기대 명세로 채택하고, 2의 생애주기에서 그 규칙을 *집행해야 하는 edge*를 표시하라.
   (b) 재현 오라클의 **부차** 단언 기대값으로 번역하라(티켓이 pass-criteria를 안 줄 때 특히).
   ⚠️ 규칙은 가설을 candidate로만 만든다 — **증상 단언은 티켓 현상에서만**, 확정은 런타임 RED 후에만(9).
   규칙이 런타임 관찰과 모순되면 런타임이 이긴다 — discrepancy를 findings.log에 기록(큐레이션 입력).

1. **후보 값(들)을 지목** — 증상이 *무엇에 관한* 값인가? 필드/슬롯/변수 단위로 구체적으로. 보통 1개지만,
   정적으로 여러 값이 의심되면 **복수 후보를 유지하라(조기에 하나로 줄이지 마라)**.
2. **생애주기를 그린다** — `produce → store/copy → consume`. **모든 복사본·캐시를 빠짐없이** 나열.
   cks 매핑: `find_callers`/`impact_analysis` = 복사본·소비자 열거, `change_history` = 생산자 변경 시점.
   ⭐ **효과-완전성**: 증상의 *관측 효과*(같은 에러·거부·틀린 값)를 내는 **경로/단계/use-site를 *전수* 열거**하라 —
   같은 에러를 반환하는 *모든* site, 처리·검증의 *모든 단계*(예: 단계가 2개면 둘 다), 의심 객체의 *모든* use-site.
   **한 경로만 보고 "여기로구나" 하면 안 된다 — 같은 효과를 내는 다른 경로를 *추론으로* 배제하는 것이 전형적 오진.**
   use-site는 `find_callers`/`search_text`로 끝까지 확인(한 곳만 봤다고 끝난 게 아니다).
3. **edge별 실패모드를 열거** (보편 분류 — 도메인 무관) —
   - produce: 안 씀 / 잘못 씀 / 늦게 씀(타이밍)
   - store: **소스가 바뀌어도 갱신 안 됨(stale)** / 키 틀림 / 복사본이 갈라짐
   - consume: 잘못된 소스를 읽음 / stale 복사본을 읽음 / 비교 로직 오류 / 전제조건 틀림 / 누락된 검증·가드
4. **각 실패모드 → 함수 1개로 매핑** — 추측 말고 `file:line`. 없으면 cks로 찾는다.
5. ⭐ **시간적 시퀀스 추적** — 증상이 **"트리거 X 이후 한동안 지속되다 사라진다"** 류이면, X *한 시점*이 아니라
   **X 이후 이벤트 시퀀스**(후속 호출·이벤트·주기적 갱신)를 따라가라. 특히 ⭐ **증상을 *해소*시키는 이벤트를
   찾아라** — 그 이벤트가 갱신/재계산하는 대상이 곧 **누락된 갱신 지점**이다. (정적 그래프는 한 시점의 연결만
   보여준다. 트리거 *직후*가 아니라 그 *뒤*에 무엇이 다시 실행되어 값을 고치는지는 직접 추론해야 한다.)
6. ⭐ **증상의 구별특징으로 반증** — 예 "한 방향만 stuck", "특정 주체만 영향", "특정 조건에서만". 그 특징을
   *설명하지 못하는* 가설은 약화한다. **단, 정적 반증은 가설을 *줄일* 뿐 *확정*하지 못한다** → 7·9.
   ⚠️ **확증편향 차단**: 경쟁 가설만 반증하지 말고, **내가 손에 든 증거(cks가 준 pack 본문·시그니처·주석)로
   *내 leading 가설*을 먼저 반증 시도하라.** 이미 받은 본문이 내 가설과 모순되면(예: "이 값은 *검증 중*에 계산됨"
   같은 주석) **그게 내 정적 추론을 이긴다 — pack을 거슬러 단정하지 마라.**
   ⚠️ **동일효과 다중경로면 정적 제거 금지**: 후보 A·B가 *같은 관측효과*(같은 거부/에러)를 낼 수 있으면, 코드만
   읽고 B를 "fire 안 함"으로 제거하지 마라 — 어느 게 실제로 fire하는지는 9(프로브)로만 확정된다.
7. ⭐ **소스까지 역추적** — stale 값을 찾아도 멈추지 마라. "이 값의 생산자는?"을 깨진 edge나 생산자에 닿을
   때까지 반복. **첫 캐시는 보통 *증상*이지 원인이 아니다.**
8. **캐시 무효화 점검** — 모든 캐시마다 "소스가 바뀔 때 무효화/갱신하는 코드가 있나?".
   invalidator 0 인 캐시 = 용의자. **단, 용의자이지 결론이 아니다.**
   ⚠️ **끌개(attractor) 가드**: "변경 후 옛 값, 영구적" 증상에서 스스로 'cache'라고 이름 붙은
   결함은 *가장 매혹적인 오답*이다(실측: 독립 5세션 전원이 같은 캐시로 수렴, 전원 오답 —
   진짜 원인은 '캐시'라 자칭하지 않는 생산층 가드였다). 캐시를 결론으로 올리기 전 필수 2가지:
   (a) **생산층 반문** — "캐시를 무효화하면 재계산은 *신선한* 소스에서 읽는가?" 소스(env/생산자)가
   티켓 시나리오(예: 빈 블록 구간)에서 갱신되는지 스텝 7의 생산자까지 확인했는가?
   (b) **시나리오 발화 확인** — 그 캐시 경로가 티켓의 조건에서 실제로 소비되는지는 9(프로브/재현)로만
   확정한다. 정적 근거(invalidator 0 · 도입 커밋)가 아무리 쌓여도 (a)(b) 없이는 competing으로 유지.
9. ⭐ **다중-후보 판별(런타임)** — 위를 다 했는데도 **후보가 2개 이상 남거나** 반증이 흔들리면(정적 코드만으론
   어느 후보가 실제로 fire하는지 모르면), **`investigative-probe` 스킬**로 증상 시나리오를 구동하며 각 후보
   지점의 런타임 값을 관찰해 가린다. **판별 전에는 단일 원인으로 확정하지 말고** competing으로 보고하라.

> ⭐ 5·7·9는 **검색·열거만으로는 안 나오는, 가장 자주 건너뛰는 세 동작**이다.
> 5를 빠뜨리면 트리거 시점만 보고 "그 다음"을 놓치고, 7을 빠뜨리면 첫 stale 복사본(증상)에서 멈추며,
> 9를 빠뜨리면 후보가 갈릴 때 *추측*으로 단일 확정해 틀린다 — 부분진단·오진의 전형이다.

## 귀결 점검 (consequence-of-change) — 같은 값, *다른 증상*의 인접 결함 (선택적, 발산)

1~9는 *주어진 증상*의 깨진 edge로 **수렴**한다(symptom-bound). 이 절은 그 위에서 한 번,
*값의 의미*로부터 **다른 증상을 낼 수 있는 인접 결함**을 **발산적으로** 점검한다(semantics-bound).
1차 수정 중에 *증상이 다른* 인접 결함을 만나는 그 추론이다(예: 어떤 임계/정책 값이 올바로 갱신되게
고쳤다면, 그 값으로 *과거에 내린 결정*을 재평가/철회해야 하는 소비자가 남아 있을 수 있다). 시니어는
1차를 파고들다 자연히 닿고, 이 절은 파이프라인도 닿게 한다.

⚠️ **2에서 열거한 consumer 집합 위에서만** 돈다(새 전역 스캔 금지 — 근거 없는 후보는 환각이다).
각 consumer C에 대해 "stale인가?"가 아니라:

  값 V가 런타임에 A→B로 *정당하게 바뀔 때*,
  (i) C는 V로 무엇을 결정/분기하는가?
  (ii) V가 바뀌면 C가 *지금 하지 않는* 어떤 동작이 필요해지는가? —
       A 전제로 내린 과거 결정의 **재평가/철회**(예: 옛 임계로 통과시킨 항목을 새 임계로 *drop*),
       새 값으로의 재계산, 캐시 무효화, 경계조건 재검사.
  (iii) 그 누락이 *이 티켓 재현과 다른* 어떤 증상을 낼 수 있는가?

각 후보는 **손에 든 코드(2에서 cks가 준 본문·시그니처)로 자기-반박을 1회** 거친다
("이미 다른 곳에서 처리되나? 의도된 설계인가?"). 반박을 못 버티면 버린다.

⚠️ **범위 경계**: 이 후보들은 *이 티켓의 수정 대상이 아니다*(재현 오라클이 *다른* 증상을 검증 못 함).
**여기서 고치지 말고**, 확신도와 함께 **기록·격상만** 한다. 확신 낮은 최적화·스타일 관찰은 별도
저-확신 레인에 두거나 생략한다(가장 노이즈가 크고, 이미 있는 메커니즘 재발견이 잦다 — 예: 이미
atomic 변수로 캐시된 값을 "메모리에 캐시하라"고 재제안).

산출: `side_findings[]` — {site(`file:line`), value, change_scenario, missing_behavior,
predicted_symptom(이 티켓과 다른), confidence, refuted_check, in_scope:false, suggested_action}.

## 산출 (diagnosis.md / plan-fix-N.md 의 Root cause 절에 반영)

- 지목한 값(들) + 생애주기: producer / 복사본 목록 / consumer
- **깨진 edge + `file:line`** (런타임으로 확인된 것 우선; 미확인 competing 후보가 있으면 그대로 표기)
- 반증으로 탈락시킨 경쟁 가설(왜 아닌지 한 줄씩) + 런타임 프로브로 판별했다면 그 관측값
- 확신도 + 무엇이 확신을 올리나(어떤 *판별변수*를 어떤 관측/재현이 보여주는가)

한 줄 트리거: **후보 값 → 모든 복사본·무효화 → 트리거 *이후* 시퀀스(무엇이 증상을 해소시키나) → 소스까지 역추적 → 후보 갈리면 런타임 프로브로 판별.**
